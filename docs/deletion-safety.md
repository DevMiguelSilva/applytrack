# Trash and master-CV deletion safety

This change replaces native confirmation at Trash-card Delete, trashed job detail Delete and Empty trash. The dialog freezes owner, route and `(id, deletedAt)` targets. Confirm and retry remove only rows still carrying those timestamps, report skipped rows and never include later arrivals. Cancel is initially focused; actions use neutral/quiet red styling, equal mobile columns and desktop right alignment. Pending blocks duplicate dispatch, Escape and dismissal. Detail success returns to Board; card/bulk stay there. Recoverable Send to trash and Restore are unchanged.

Master-CV deletion no longer asks for a replacement. Generated documents are not written during deletion. Saved jobs, including implicit-default and Saved Trash references, retain the removed ID with `needsCvSelection`; linked searches retain their ID, pause and require explicit reselection followed by activation. Submitted history remains untouched. Only future new items inherit the deterministic remaining default (ASCII template-ID order, matching SQL C collation). The dialog names that default. The last CV cannot be deleted.

Stored resume/letter preview, Copy, DOCX/application-folder export and print resolve actual stored output/snapshot independently of the live generation source. Legacy partial output uses blank missing fields, never another live CV or fabricated facts. Choosing another source does not generate or replace files. Existing completeness requirements still govern Mark as applied. Live scoring, skill claims, generation and save retries require a valid source. Fingerprinted saves reject stale library/job inputs; submitted document writes are rejected.

## Local transactions and recovery

All affected local writers read current storage under one shared queue and, where available, the origin Web Lock `applytrack-local-mutation`. Multi-store deletion first writes `applytrack-local-mutation-v1` containing owner and exact previous values. Failure rolls back; if rollback also fails the journal remains. The next compatible locked read replays it before continuing. Legacy CV journals are still recovered. Do not clear journals, browser storage or replace data with sample records to fix a failed deletion. Restore storage capacity/access and reload this compatible client; a mismatched journal owner fails closed. Browsers without Web Locks retain same-tab serialization only; simultaneous local editing across tabs is unsupported there.

CV deletion journals library/jobs/searches/Inbox and never documents. Purge journals jobs/documents together. Storage events refresh other tabs; mutation revisions prevent older loads replacing newer writes. Cloud updates patch rows rather than resurrecting deleted jobs; zero-row updates fail. Cross-device SQL row locks and transactional predicates determine committed state. Route/account changes invalidate UI before dispatch and ignore stale results, but cannot recall a request already dispatched: a server-committed deletion remains committed even if its initiating view closes.

To roll back UI, preserve database columns/RPCs and all journals/documents. Do not drop flags or automatically reassign archived IDs. Prefer a forward fix or restore affected data from a verified backup; permanent deletion has no product Undo. Reverting to a pre-flag frontend requires resolving affected records explicitly and closing active sessions, not blindly clearing flags. The migration deliberately has no destructive down migration.
